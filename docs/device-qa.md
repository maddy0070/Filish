# FILISH V4.1 — Device QA pass

**This round could not be performed in the build environment.** There is no
physical device and no emulator: `adb devices` returns an empty list, no
emulator package is installed, and `/dev/kvm` does not exist so one could not
run. Nothing in this document reports a frame rate, a decode time or a memory
figure, because none were observed.

What follows is everything needed to run the pass on real hardware, plus the
findings that *were* measurable here.

---

## 1. What you need

| | |
|---|---|
| APK | `app-release.apk` on the GitHub release, or `app-debug.apk` from `./gradlew :app:assembleDebug` |
| Build to use | **the debug APK** — the QA readout and dataset builder only exist in debug builds |
| Permission | grant All files access when asked; the QA datasets themselves need none |

**Verified here (MEASURED):** release APK 3.55 MB, debug 13.3 MB; package
`com.filish` unchanged; **no INTERNET permission in either build**; permission
set unchanged from V4 (`READ_EXTERNAL_STORAGE` ≤32, `WRITE_EXTERNAL_STORAGE`
≤29, `READ_MEDIA_*`, `MANAGE_EXTERNAL_STORAGE`).

## 2. Turn the instrumentation on

Settings → **Device QA (debug build)** — the section only renders when
`BuildConfig.DEBUG` is true.

- **QA readout** → a monospace slab above the list showing: row/item/folder
  counts, the current mass scale and largest magnitude seen, how many distinct
  mark widths the directory produces, how many marks are at the floor and at
  the ceiling, measurement progress (settled / in flight / pending), selection
  count, sort, and whether media signatures are on.
- **Media signatures** → leave **OFF** for scenarios A–D. Only turn it on for
  scenario E, and only on your own camera roll.

## 3. Build the datasets

Settings → **QA datasets** → Build. Everything lands in
`Android/data/com.filish/files/filish-qa/`, needs no permission, and is removed
by uninstalling or by "Delete all QA datasets".

Files are **sparse** — they report a real size but occupy almost no space. A
sparse file is not a photograph, so **scenario E cannot use these**; point
FILISH at your real DCIM for that one.

| Directory | What it is for |
|---|---|
| `01-mixed-5000` | 5,000 entries. Scroll, fling, select. The density test. |
| `02-tiny` | 2,000 files under 40 KB. Do the marks vanish or turn to noise? |
| `03-huge` | 12 files, 2 KB to 8 GB. Does one 8 GB file crush everything else? |
| `04-ugly` | Unicode, emoji, spaces, brackets, 200 chars, zero bytes, no extension. |
| `05-late-largest` | Small files plus a deep folder that resolves last and is biggest. **The spine test.** |
| `06-same-size` | 40 identical-size RAW files. The mark-fusion test. |
| `07-relative-a` / `08-relative-b` | The same 40 MB file among tiny neighbours and among huge ones. |

## 4. The scenarios

Each has an **expected observation**. Report anything that differs — and note
that P · Spine is deliberately unfamiliar, so "this looks unusual" is not by
itself a failure. A bug is something *wrong*, not something new.

### A · Normal directory (your own files)

- [ ] Rows read as intentional; names and metadata legible
- [ ] **No card, panel, border or shadow anywhere at rest** — substrate, mark, ink only
- [ ] The spine reads as generated by the content, not as a progress bar or a rail
- [ ] Marks are separated from each other and detached from the text

### B · `02-tiny` — a wall of small files

Expected: most marks near the 4dp floor, but with visible variation between a
900 B file and a 40 KB one. **Failure:** a flat uniform stripe that says
nothing, or marks so thin they read as an artefact.

- [ ] Variation is visible
- [ ] Nothing looks like a rendering glitch

### C · `03-huge` — a few enormous files

Measured here (JVM render, `v41-huge-files.png`): 8 GB → 6.4 → 4.1 → 2.0 →
900 MB → 120 MB → 4 KB → 900 B produced a clear descending staircase with the
two smallest at the floor. Confirm it looks the same on hardware.

- [ ] A descending staircase, not two blocks and six slivers
- [ ] The 900 B file is still visible

### D · Mixed media

- [ ] Kinds distinguishable without icons (mark hue + the word in the metadata)
- [ ] Folders do not dominate — they use a neutral, deliberately muted in V4

### E · Photo-heavy — **media signatures**

Turn the flag on. Use your real camera roll, not the QA datasets.

**NOT MEASURED anywhere. This is the reason the flag exists.**

- [ ] Cold scroll through ~500 photos — any stutter?
- [ ] Fling to the bottom and back — does it degrade?
- [ ] Watch memory (Android Studio profiler or `dumpsys meminfo com.filish`)
- [ ] Do marks visibly differ per photo, or do they all go muddy brown?
- [ ] Turn the flag **off** and compare: is the difference worth any cost?

Classify at the end: **A** excellent and cheap · **B** useful but a risk ·
**C** visually weak · **D** unnecessary. If anything but A, leave it off.

## 5. `01-mixed-5000` — the 5,000-file UI test

The pipeline half is MEASURED (JVM): 5,040 entries listed in **66 ms**, whole
spine geometry in **4 ms**. The rendering half is what you are testing.

- [ ] Initial appearance — how long until rows are on screen?
- [ ] Slow scroll · fast fling · reverse fling · jump to the end
- [ ] Select 10, then 100, then Select All
- [ ] Re-sort by size and by date while at 5,000
- [ ] Watch for: frame drops, input latency, layout jumps, text clipping,
      memory growth, GC pauses

Use `adb shell dumpsys gfxinfo com.filish framestats` for real numbers, or
Developer options → Profile HWUI rendering for a visual read.

## 6. `05-late-largest` — the spine stability test

**The most important scenario.** Open it and watch the left edge while the
deep folder measures.

MEASURED here against the real `SizeResolver` (`SpineStabilityTest`):

| | |
|---|---|
| Partial results for a ~9.6 GB tree | 3 |
| Rescales | 1 |
| **Scale decreases** | **0** |
| Bystander mark movement in one step | 11.0 dp |
| Measured folder's mark in one step | 20.9 dp |
| Late-largest: 500 MB file | 25.9 dp → 21.7 dp as the scale rose 2³⁰ → 2³² |

**A bug was found and fixed by this measurement.** The new proportions were
correct — a 9.6 GB folder had genuinely appeared — but they were arriving in a
single frame, which snaps. The mark now settles over `Motion.CONSIDERED`
(320 ms) when the scale changes. Quantisation caps how often that can happen.

- [ ] The spine does **not** oscillate or breathe continuously
- [ ] Marks **never** get narrower and then wider again
- [ ] When the big folder lands, the whole spine **settles** rather than snapping
- [ ] Adjacent marks never fuse into one bar (see also `06-same-size`)

## 7. `07-relative-a` vs `08-relative-b` — the relative-scale question

**This is the open design question, and it is yours to settle.**

Open A, find `THE-SAME-FILE-40MB.bin`, note its mark. Open B, find the same
file, compare. Rendered here as `v41-relative-scale-night.png`: the mark is at
the ceiling in A and about 10 dp in B. The figure reads 40 MB in both.

Then answer honestly:

- [ ] Does the difference read as **useful context** ("this is the big thing
      here" / "this is the small thing here")?
- [ ] Or does it read as the mark **lying** about the file?

**Known limitation, characterised here (MEASURED):** the channel discriminates
well when a directory spans many doublings and poorly when it spans few. A
folder of 2–7 GB videos is only ~1.8 doublings wide, so every mark lands near
the ceiling and the spine goes flat. Whether that is an honest report ("these
are all big") or a failure is exactly what the device pass should decide.

**Smallest correction if it is a failure — NOT IMPLEMENTED:** make
`Mass.SPAN` adaptive, using the listing's actual spread clamped to a sensible
range, instead of a fixed 16 doublings. This would spend the whole channel on
whatever range is present. It is deliberately not built, because deciding it
from theory is what this round is meant to stop.

## 8. `04-ugly` and `06-same-size`

- [ ] Every hostile name renders; nothing crashes or blanks
- [ ] The 200-character name wraps and the row grows
- [ ] Zero-byte files get a floor mark, not a full-width one
      *(this was a real bug, fixed in V4 — see `MassTest`)*
- [ ] In `06-same-size`, 40 identical RAW files show **40 separate marks**,
      not one continuous bar

## 9. Typography and accessibility

MEASURED here (`RowMetricsTest`, real layout at font scales 1.0 / 1.3 / 2.0):
never below the 48 dp floor, always taller when type grows, taller again when a
name wraps, and ten rows exactly ten rows tall. At 2.0× the metadata line
wraps rather than truncating (`v4-very-large-font.png`).

On device:

- [ ] Settings → Display → Font size at largest; also Display size
- [ ] No clipping; metadata wraps; touch targets still comfortable
- [ ] The spine does not collide with text at any scale
- [ ] **TalkBack**: each row announces name, kind, size and date. A folder still
      being measured says "so far, still measuring"
- [ ] With TalkBack alone, confirm the spine is not needed to know a file's size
- [ ] Reduced motion (Developer options → animation scales off, or
      Accessibility → Remove animations): the mark jumps to its width instead
      of settling

## 10. Press and selection

- [ ] Press: immediate, **no ripple**, no scale, no shadow, no glow
- [ ] Only the pressed row responds — neighbours do not move
- [ ] Press while scrolling does not trigger a click
- [ ] Selection: the object gains a solid body; **no checkbox-first, no blue**
- [ ] Adjacent selections **merge into one continuous mass**
- [ ] Non-adjacent selections read as separate islands with substrate between
- [ ] Select All at 5,000 — does it lag?
- [ ] A selected mark keeps both its width and its hue

---

## 11. Light and dark

- [ ] Dark reads as a **place**; day reads as a **page**
- [ ] No muddy dark surfaces, no washed-out day surfaces
- [ ] Metadata legible in both — in direct sunlight if you can get outside
- [ ] Marks not overly bright in dark, not washed out in day

---

## 12. The anti-generic check

Cover the path rail and the action bar. Look only at the list.

- [ ] Could this be Google Files, Samsung My Files, Apple Files, Solid
      Explorer, or a stock Compose list?

If yes: **do not ask for decoration.** Say which structural thing makes it
generic — density, the spine's weight, the typography, the substrate — so the
fix is structural.

---

## 13. Reporting back

For each finding note **what you did**, **what happened**, **what you
expected**, and whether it is a **bug** or a **preference**. Screenshots help
most for anything visual; `adb logcat -d > log.txt` helps most for anything
that crashes or hangs.
